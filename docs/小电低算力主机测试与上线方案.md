# 小电低算力主机：测试、实现与上线交接

日期：2026-09-08。交付对象：主机部署同事。

目标：不扩充知识数据，选出能在实际环境稳定运行的配置，完成“小电身份注入 → 问题理解 → 混合检索 → 基于证据回答 → 来源跳转”，再正式上线。

当前基线为仓库 `main` 的 `47c2e2d`，已有本地验收和交接包；生产上线尚未验收。本文是下一阶段执行计划，其中新增参数、ONNX 接入等尚未实现。

## 1. 部署路线：先选一个

**优先：整套知识服务迁到内网算力机。** 现主机保留电台业务后端；知识服务、BGE-M3、reranker、Qdrant 和知识数据库一起迁移。业务后端通过 `BACKEND_RAG_URL` 和私有凭证访问。保留原模型先验收，减少质量变化。只把单个模型改成远程调用需要新增适配，当前并非改 URL 即可。

**只有现机可用：保留 BGE-M3 召回，测试轻量重排。** 问题理解和答案生成使用已有可达模型服务，不在这台 4 核、8GB、无 GPU 主机上再部署生成大模型。

虚拟化管理员先核实宿主 CPU、资源配额与迁移要求，再决定使用 `host-passthrough` 或兼容 CPU 模型。安排正常关机后修改、启动，重新检查指令集和实测速度；不照抄强制 `destroy`，不预设 AVX2 或固定加速倍数。

## 2. 测试前必须统一的口径

- 当前代码最多重排 **60 个候选**，输入上限 **1024 token/对**；`batch_size=8` 只是每批数量。报告的 `8×512` 不能代表完整问答的重排耗时。
- `BACKEND_AI_CONTEXT_ITEMS` 控制重排后选取数量，调小它不会减少前面的重排计算。
- 随机结构基准用于筛选算力量级；最终必须用真实权重、tokenizer、中文问题与片段测试。英文 MiniLM-L6 的速度不能直接套用到多语模型。
- 交接官方库为 **567 份文档、1562 个片段**，不是旧版 4149 片段。实际导入后以 `/status` 为准。
- `treehole` 的 `MemoryMax=2G` 是服务上限，不是实际占用。知识服务独立进程、独立 systemd 单元，不放进业务服务的限制中。

先记录 `lscpu`、`free -h`、`vmstat 1 30`、`systemctl show treehole -p MemoryCurrent -p MemoryMax -p ControlGroup`。关注 CPU steal、实际内存、换页和普通业务接口延迟。

## 3. 现机模型与参数筛选

只测试以下两种重排模型，第一种质量不足再测第二种：

| 顺序 | 模型 | 注意事项 |
|---|---|---|
| 1 | `cross-encoder/mmarco-mMiniLMv2-L12-H384-v1` | mMARCO 包含中文；这是 L12 多语模型，不能按 11M 参数或 L6 的速度估算 |
| 2 | `BAAI/bge-reranker-base` | 支持中英文，但基于 XLM-R base，仍有大词表；不能按普通 BERT 的内存估算 |

先测试 FP32，选出可行候选后再比较 ONNX INT8；不预设量化一定快 2–3 倍或总内存降至四分之一。ONNX Runtime 必须在目标 CPU 上实际完成推理，不能只验证导入成功。

| 参数 | 初始测试 | 追加测试条件 |
|---|---|---|
| 进入重排的候选数 | RRF 排序后的前 8 条 | 证据覆盖不足再试 12、16 条 |
| 问题＋片段的合计长度 | 256 token | 时间、材料、例外被截断时比较 512 |
| batch size | 1、2、4 | 选择实测结果，不默认越大越快 |
| CPU 线程数 | 2、4 | 同时观察业务接口延迟 |
| 模型进程 | 1 | 避免多个 worker 重复加载权重 |

先预热 3 次，再测完整候选集合的耗时，包含 tokenizer、所有批次和排序。明显超预算的组合立即停止，不跑完整矩阵。只对胜出的配置执行接口和并发测试。

## 4. 胜出后需要实现的改动

以下改动在测试分支实现，记录提交号；不要直接修改正在运行的发布目录。

1. **限制重排输入量。** 在 `knowledge_service/engine.py` 中，保持双路召回和 RRF，完成文档状态、适用范围过滤及去重后，按 RRF 顺序取前 N 条再重排。保持原始证据和相邻段落机制。
2. **参数化模型推理。** 在 `knowledge_service/models.py` 中新增候选数、重排长度、batch 和线程配置。可命名为 `KNOWLEDGE_RERANK_CANDIDATES/MAX_LENGTH/BATCH_SIZE`、`KNOWLEDGE_TORCH_THREADS`；这些目前不是已有开关。重排截断不修改规范原文，也不把最终回答上下文一并截成 256 token。
3. **更新模型与阈值。** 固定模型 revision、tokenizer、精度和文件 SHA256，更新模型路径及 revision 配置。重新校准 `KNOWLEDGE_RERANK_THRESHOLD`，不得直接沿用旧模型的 `0.05`，也不得靠放行无关资料满足召回。
4. **若选 ONNX。** 显式实现 tokenizer、ONNX 输入输出、单标量分数及激活处理；验证排序和阈值。不能仅将 ONNX 文件路径填进当前 PyTorch 加载器。不新增静默回退模型或模板回答。
5. **保留问答契约。** 服务端持有“小电”系统提示词；问题规划先写完整需求、最后判断 intent；生成保留用户原问题和主题补全，不重新注入历史助手事实；答案先生成正文，再选择 S1/S2 证据编号，后端映射真实段落 ID。生成供应商必须支持严格 `json_schema`。
6. **补齐性能记录。** 每题记录查询改写数量、编码耗时、候选总数、真实长度/截断比例、重排耗时、检索耗时、生成耗时、总耗时和 traceId。时延应包含排队，不只记录模型前向时间。

## 5. 数据、环境与更新安排

- 优先在算力机建索引，迁移匹配的知识数据库、Qdrant snapshot、活动索引元数据和模型配置；不能只复制向量。若目标端重建，先离线完成，再进入在线测试。
- 仅换 reranker、保持 embedding 和切片不变时，不需要重建向量；改变 embedding 模型或编码方式则必须建新索引并验收。
- 使用独立 Python 3.11 环境；离线包按目标 Linux 发行版和架构准备，不复制 Windows venv，不升级现有业务 Python。
- 官方自动刷新继续关闭：当前需先修复“人工下架状态可能被刷新覆盖”的问题。
- 论坛同步已有增量跳过机制。先测少量新增、修改时对在线问答的影响，再决定同步频率；不是每分钟全量重建。

## 6. 验收与通过标准

使用现有固定题目和资料，不扩量。依次测试：真实模型 → 私有 `/search` → 电台 `/api/ai/chat` → 实际页面及来源跳转。

沿用 `docs/ai/local-cases.json` 的 11 个业务用例、4 个随机证据检查、8 个知识生命周期检查。金额、时间、材料、校区、身份、追问及未知信息边界必须正确；资料撤回或帖子私密/删除后不得继续作为证据。

**现有 `scripts/*local*` 验收工具含本地地址和隔离会话假设，不可原样指向生产。** 同事应适配目标地址与授权测试账号；随机文档、帖子改私密/删除等变更测试只在同构隔离库执行。生产入口只做正常账号的只读问答验收。

| 项目 | 本轮建议通过标准（目标，非已测结果） |
|---|---|
| 质量 | 11 个业务用例、4 个随机证据检查、8 个生命周期检查全部通过；不得以拒答替代有证据的答案 |
| 证据 | 正确原文进入最终上下文，引用确实支持答案，页面能打开原文 |
| 暖态时延 | 单请求重排 P95 ≤2秒；完整检索 P95 ≤3秒；并发2的检索 P95 ≤5秒 |
| 完整回答 | 建议暖态 P95 ≤25秒；分别报告问题理解、检索、生成耗时，若超标定位对应模型服务 |
| 主机资源 | 无 OOM、无持续换页，峰值期间可用内存约≥1.5GB |
| 业务影响 | 普通电台接口 P95 相对测试前恶化≤20% |

计时与质量分开：重复现有检索题至少取得 50 次有效检索请求，分别测并发1、2；冷启动单列。P95 只代表本轮固定负载，不代表全领域或高并发能力。测试过程中同时访问普通业务接口，并包含一次少量增量更新。

## 7. 上线与回滚顺序

1. 保存当前业务代码、配置和 Web 发布版本；备份知识 SQLite、匹配的 Qdrant snapshot、活动索引与模型清单。业务账号库不得被知识库导入或回滚覆盖。
2. 部署独立知识服务和索引。部署模板位于仓库 `deploy/`；服务用户、路径按目标环境调整。私有凭证独立保存，API 仅允许业务主机访问；跨不可信网络须使用 TLS 或受控隧道。
3. 将胜出参数、模型 revision、量化产物及实测结果写入本次发布清单。确认 `/status`、一次真实检索和一次增量更新均正常，不能只看 `/health` 就切流量。
4. 配置业务后端的 `BACKEND_RAG_URL/API_KEY` 和已验收的生成服务，发布对应后端与 Web。Nginx AI 代理超时覆盖完整处理阶段；现客户端为165秒，可将代理设为180秒，但不以加大超时代替性能达标。
5. 先用授权账号在真实电台验证“你是谁＋研究生选课时间”、访客上网、追问和来源链接。观察业务延迟、内存、错误日志后再开放正常使用；持续观察至少一个实际使用高峰。
6. 出现关键事实错误、失效证据泄漏、OOM、持续换页或明显业务退化时，人工切回备份的发布与配置。知识数据有变更时恢复匹配的数据库/索引组合；不自动切回旧词法检索掩盖问题。
7. 提交并推送最终实现、配置模板及验收报告，记录最终 Git 提交号、模型 revision、索引版本、部署时间与验收 traceId。密钥、业务库和模型权重不进 Git。完成主机验收后才标记生产上线完成。

若现机的轻量配置不能同时满足速度和质量，转用内网算力机；不要继续牺牲关键证据长度来强行上线。
