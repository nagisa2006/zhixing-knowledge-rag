# 生产主机算力实测（《小电低算力主机测试与上线方案》的数据附录）

日期：2026-09-08 首测，2026-09-10 CPU 模式变更后复测并完成真实权重测试。测量对象：`zhixing.xidian.edu.cn` 所在主机（堡垒机资产 2466，主机名 `ubuntu-KVM`）。

《小电知识库诊断与迁移方案》与《手动部署与本地验收》写明「独立推理环境必须支持 CUDA，
或明确配置 CPU 并重新测量延迟；当前主机性能尚未核实」。本文提供该核实的原始数据，
供《小电低算力主机测试与上线方案》第 3 节的模型与参数筛选使用。

第四节之前为随机结构的算力筛选，**第四节之二已补上方案 §3 要求的真实权重测试**
（真实模型、真实 tokenizer、真实中文片段，计时含 tokenizer 与排序）。

## 一、结论

2026-09-08 首测时该虚拟机为 QEMU 默认 `qemu64` CPU 模型，只有 SSE/SSE2/SSE3。
2026-09-10 虚拟化管理员已将其改为兼容模型 **Intel Xeon (Icelake)**，暴露
`avx2` `fma` `avx512f` `avx512_vnni` 等完整指令集。同一组基准实测加速
**5.5–6.9 倍**。本文两轮数据都保留，第四节可见。

按现有代码的实际重排负载（下节核实：最多 60 对 × 1024 token）换算到改后主机：

| 重排模型 | 满负载一次查询 |
|---|---|
| XLM-R large（现固定的 `bge-reranker-v2-m3`） | 约 100 秒 |
| `bge-reranker-base` | 约 29 秒 |

**加速 6 倍也不足以在不限制输入量的前提下上线。** 方案 §4.1「限制重排输入量」
是前提条件而非可选优化。

限制输入量之后，按方案 §6 的「单请求重排 P95 ≤2 秒」反推各模型的 token 预算：

| 重排模型 | 2 秒可用 token 量 | 相当于 | 8×256 实测换算 | 8×512 实测换算 |
|---|---|---|---|---|
| XLM-R large（现固定） | 约 1200 | 仅 4 候选 × 256 | 3.34 s ✗ | 6.68 s ✗ |
| `bge-reranker-base` | 约 4200 | 8×512 或 16×256 | **0.97 s ✓** | **1.94 s ✓** |
| mMiniLMv2-L12（推算） | 约 15000 | 基本不受约束 | 0.27 s ✓ | 0.54 s ✓ |

**建议调整方案 §3 的测试顺序：先测 `bge-reranker-base`。** 原顺序把
mMiniLM 排在前面，前提是「base 太慢」（改前 8×256 需 5.4 秒）。该前提已不成立，
而 base 的中文质量优于多语 MiniLM，因此应先测 base，mMiniLM 降为退路。

**保留现固定模型这条路不建议采用。** 它只买得起 4 候选 × 256 token，低于方案 §3
设定的 8 条初始值（§3 还预留了「覆盖不足再试 12、16 条」），且 256 token 会截断
时间/材料/例外。保留固定模型本可完整沿用 `docs/ai/local-*.json` 验收基线、免去
§4.3 的阈值重校准，改动面最小 —— 但证据覆盖低于方案自身起点，代价过高。

召回侧无需改动：BGE-M3 编码一次问题实测 135 ms。

**内存**：换 base 后两模型合计约 3.4 GB（BGE-M3 2.3 GB + base 1.1 GB），
保留 v2-m3 则约 4.7 GB（同为 XLM-R large）。改后主机 MemAvailable 7.16 GB，
省下的 1.3 GB 对方案 §6「峰值可用内存 ≥1.5 GB」是实质差别。
方案 §3 提醒 base「仍有大词表」正确：其词表 250002×768 单独约 0.77 GB。

**ONNX INT8**：改后 CPU 带 `avx512_vnni`（int8 点积硬件加速），该路线在本机很划算。
但 base 走 fp32 已达标，建议先按 fp32 上线、把 int8 留作余量，
以免引入 §4.4 要求的 ONNX 输入输出、激活与阈值的额外实现和验收。

## 三、硬件实况

| 项 | 值 |
|---|---|
| OS | Ubuntu 22.04.2 LTS |
| CPU（2026-09-10 起） | `Intel Xeon Processor (Icelake)`，4 核 @ 2194 MHz |
| CPU 指令集 | `ssse3` `sse4_1` `sse4_2` `avx` `avx2` `fma` `f16c` `bmi2` `avx512f` `avx512_vnni` 全部可用 |
| CPU（2026-09-08 首测时） | `QEMU Virtual CPU version 2.5+`，仅 `sse` `sse2` `pni` `mmx`，约 56–67 GFLOP/s |
| 内存 | MemTotal 7.9 GB，MemAvailable 7.16 GB（首测时 6.6 GB），Swap 2 GB |
| GPU | 无（`/proc/driver/nvidia`、`/dev/nvidia*` 均不存在） |
| 磁盘 | `/` 98 G，可用 78 G |
| Python | **仅 3.10.12**，无 3.11（部署文档要求独立 3.11 环境） |
| `/opt` | 空 |

首测时的 `qemu64` 是 QEMU 默认模型，遮掉了物理 CPU 的现代指令集；即便如此 SSE2 路径
仍有约 56 GFLOP/s，说明遮住的是指令集而非主频或核心数。管理员改为 Icelake 兼容模型后
指令集完整可用。`vmstat`、CPU steal、实际内存占用按方案 §2 要求另行采集，本文未采。

`avx512f` 执行时部分 CPU 会降频，可能影响同机业务后端。Icelake 这代比早期
Skylake-SP 温和，但方案 §2 要求的「同时观察业务接口延迟」仍应执行。

## 四、原始实测数字

方法：未下载真实权重。用 PyTorch 按 XLM-RoBERTa-large 等三种结构
（层数 / hidden / 头数 / intermediate）搭随机权重 encoder 测前向耗时。
环境 `torch 2.6.0+cpu`、`torch.set_num_threads(4)`、系统 Python 3.10.12。

### 改后（Icelake，2026-09-10）

| 结构 | 编码器参数 | 1×32 | 8×512 | 4×256 |
|---|---|---|---|---|
| XLM-R large（24L / 1024 / 16H / 4096） | 302 M | 135 ms | 6678 ms | 1298 ms |
| BERT base（12L / 768 / 12H / 3072） | 85 M | 29 ms | 1939 ms | 393 ms |
| MiniLM-L6（6L / 384 / 12H / 1536） | 11 M | 5 ms | 271 ms | 59 ms |

### 改前（qemu64，2026-09-08）

| 结构 | 1×32 | 8×512 | 4×256 |
|---|---|---|---|
| XLM-R large | 352 ms | 36734 ms | 8514 ms |
| BERT base | 92 ms | 10893 ms | 2424 ms |
| MiniLM-L6 | 14 ms | 1861 ms | 375 ms |

改前另一轮独立测量（XLM-R large）：`4×512` 18205 ms、`8×256` 16969 ms、`1×32` 375 ms，两轮一致。

**实测加速比**：重排负载 5.5–6.9 倍，召回小负载 2.6–3.2 倍（小张量下向量化收益较小）。

**耗时与总 token 数（batch × seq）成正比**，两轮都成立。改前 `4×256`（1024 token）
是 `8×512`（4096 token）的 1/4，实测 8514 ms 对 36734/4 = 9183 ms。据此归一化：

| 结构 | 每 1000 token（改后） | 每 1000 token（改前） |
|---|---|---|
| XLM-R large | 约 1630 ms | 约 8970 ms |
| BERT base | 约 473 ms | 约 2660 ms |
| MiniLM-L6 | 约 66 ms | 约 450 ms |

第一节的换算值均由「改后」一列乘以对应 token 数得出。

**边界**：层数、维度、序列长度与真实模型一致，FLOPs 量级可信；但注意力实现与算子融合
和 `transformers` / `sentence-transformers` 不同，真实模型大概率更慢，本文数字视为下限。
随机权重只反映算力，与检索质量无关。方案 §3 首选的
`cross-encoder/mmarco-mMiniLMv2-L12-H384-v1` 是 L12 多语模型，本文只测到 L6，
其数字按层数翻倍外推，未实测。

### 内存

单个 XLM-R large 模型峰值 RSS **2344 MB**，其中 250002×1024 的词表嵌入独占约
**1168 MB** —— 内存大头在词表不在编码器。换小编码器省算力，但只要沿用 XLM-R 词表，
内存省不下来。方案 §3 对 `bge-reranker-base`「仍有大词表，不能按普通 BERT 估算」
的提醒与此一致。

`treehole` 服务的 `MemoryMax=2G` 是上限而非实际占用，本文不据此推算余量；
实际占用按方案 §2 用 `systemctl show treehole -p MemoryCurrent` 采集。

## 四之二、真实权重实测（方案 §3 的参数网格）

`BAAI/bge-m3` 召回 + `BAAI/bge-reranker-base` 重排，真实 tokenizer，
测试材料为仓库 `_db_service.py` 中 30 条真实中文知识条目拼接到目标长度。
每组预热 3 次，计时含 tokenizer、全部批次与排序（即 `models.rerank()` 全程）。
`max_length` 管的是问题+片段的合计长度，与方案 §3 表述一致。

### 4 线程（推荐）

| 长度 | 8 候选 | 12 候选 | 16 候选 |
|---|---|---|---|
| 256 | 821 ms ✓ | **1189 ms ✓** | 1576 ms ✓ |
| 512 | 1618 ms ✓ | 2434 ms ✗ | 3235 ms ✗ |

### 2 线程

| 长度 | 8 候选 | 12 候选 | 16 候选 |
|---|---|---|---|
| 256 | 1451 ms ✓ | 2184 ms ✗ | 2916 ms ✗ |
| 512 | 3239 ms ✗ | 4860 ms ✗ | 6885 ms ✗（触发跳过） |

上表取每组中最优的 batch。**batch 几乎无影响**（同组内差 ≤10%，batch=4 略优），
**线程数是最大的单一变量**（4 线程比 2 线程快约 1.75 倍）。
召回侧编码一个问题：4 线程 144 ms，2 线程 155 ms。

### 建议默认参数

**4 线程 / 长度 256 / 候选 12 / batch 4 = 1189 ms。**
在 §6 的 2 秒预算内留约 40% 余量（P95 高于单次测量），候选数高于方案 §3 的 8 条起点。

两个等价工作点的取舍是质量问题而非延迟问题，需由 §6 判定：

| 工作点 | 耗时 | 取舍 |
|---|---|---|
| 16 候选 × 256 | 1576 ms | 证据覆盖更广，长材料清单会被截断 |
| 8 候选 × 512 | 1618 ms | 单条证据更完整，候选数回到下限 |

若 §6 验收显示截断丢失时间/材料/例外，切到 8×512；若显示覆盖不足，切到 16×256。

### 其余 §6 指标

| 指标 | 实测/推算 | 标准 |
|---|---|---|
| 单请求重排 | 1189 ms（推荐参数） | ≤2 s ✓ |
| 完整检索 | 约 1.4 s（+ 编码 144 ms 及 BM25/Qdrant 开销） | ≤3 s ✓ |
| 并发 2 检索 | 约 2.7 s（全局锁串行，见第二节） | ≤5 s ✓ |
| 峰值内存 | 3138 MB，余 4 GB | 可用 ≥1.5 GB ✓ |

峰值 3138 MB 偏高：测试脚本为每个 `max_length` 重新加载 reranker，`del` 后
torch 未即时归还，RSS 从 2135 累积到 3138。生产只加载一次，稳态约 2.4 GB。

### 与合成基准的对照

合成基准预测 base 的 8×512 为 1.94 s、8×256 为 0.97 s；真实实测 1.62 s 和 0.82 s。
**真实模型略快于合成预测**，与本文此前「真实模型大概率更慢、合成数字视为下限」的
保留意见方向相反，该保留意见撤销。合成筛选对本例的选型是可靠的。

## 五、建索引的时间

交接官方库 567 份文档、1562 个片段（以导入后 `/status` 为准）。嵌入侧
`max_seq_length=1024`，以此为上界：

```
改后：1562 × 1024 token × 1.63 ms/token ≈ 43 分钟
改前：1562 × 1024 token × 8.97 ms/token ≈ 4 小时
```

片段实际长度普遍低于 1024 token，所以这是上界而非预期值。

**CPU 变更把全量重建从「只能夜间批处理」降到了 45 分钟以内**，
自动刷新与论坛同步定时任务未进入正式部署；恢复前仍须验证增量更新对在线查询的模型锁竞争，
这一点不因加速而消失。

## 六、其它核实到的事实

- **Python 版本不符**：部署文档要求独立 3.11 环境，现机只有 3.10.12。
  无外网下装 3.11 需自带 deb 或源码编译
- **一个被证伪的假设**：曾判断预编译 torch wheel 需要 SSE4.2/AVX2、在这颗 CPU 上
  `import torch` 会 SIGILL。**实测通过** —— `torch 2.6.0+cpu` 正常导入，
  256×256 矩阵乘 0.6 ms。PyTorch CPU wheel 有标量回退路径。后续判断不要再基于该前提
- **磁盘不是约束**：78 G 可用
- **传输量级**：现有发布包 40 MB 经堡垒机 SFTP 约 11 秒；torch CPU wheel 170 MB 约 25 秒。
  两个 BGE 模型合计 4–5 GB，同速率约 10–15 分钟，但大文件在该通道上的稳定性未验证

- **CPU 变更后的加速比已实测**：5.5–6.9 倍（重排负载）。此前本文按方案 §1 要求
  未做预估，现以实测替代
- **ONNX INT8 的加速比与内存下降幅度仍未实测**，方案 §3 要求不预设，本文不给数字。
  改后 CPU 带 `avx512_vnni`，该路线值得测，但 fp32 已达标时不必作为上线前提

## 七、复现

脚本已在生产机 `/home/ubuntu/treehole/incoming/`：`torch-smoke.tar.gz`
（torch 2.6.0+cpu 及依赖，9 个 wheel，183 MB）、`bench.sh`、`bench.py`、`bench2.py`。
只写 `~/torch-smoke` 与 `/tmp`，不装 pip、不建 venv、不动 systemd。

```bash
mkdir -p ~/torch-smoke
tar -xzf /home/ubuntu/treehole/incoming/torch-smoke.tar.gz -C ~/torch-smoke
cp /home/ubuntu/treehole/incoming/bench.sh \
   /home/ubuntu/treehole/incoming/bench.py \
   /home/ubuntu/treehole/incoming/bench2.py ~/torch-smoke/

bash ~/torch-smoke/smoke.sh            # torch 能否在这颗 CPU 上运行
bash ~/torch-smoke/bench.sh bench.py   # XLM-R large 单尺寸详测
bash ~/torch-smoke/bench.sh bench2.py  # 三档尺寸对比

rm -rf ~/torch-smoke
```

2026-09-10 的 CPU 模式变更即用同一组脚本复测，故两轮可直接对比。
后续若再调整 CPU、线程数或改用 ONNX，仍应复用这套脚本以保持可比性。
